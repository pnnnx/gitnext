# gitnext — полное руководство

## Цель

**gitnext — слой между кодом и агентом.** Агент находит, понимает и правит код за минимум токенов, а человек за минуту видит, что в проекте есть, что меняется и что делал агент.

Метрики (проверяет `gitnext bench` на любом репозитории):

| Задача | Цель | ripgrep | requests | cJSON | tinyxml2 |
|---|---|---|---|---|---|
| сориентироваться в директории | ≤ 10% от чтения файлов | 4% | 3% | 1% | 1% |
| найти и понять символ | ≤ 25% от grep + чтения файла | 1% | 4% | 1% | 1% |
| изменить одну функцию | ≤ 5% от «прочитать и переписать файл» | 0.4% | 3% | 1% | 0.4% |
| итого по 5 типовым задачам | — | −99% | −98% | −99% | −99% |

Git, оптимизированный под ИИ-агентов. Репозиторий остаётся обычным git (GitHub, CI и `git` работают как раньше), а поверх него gitnext держит смысловой слой:

- **граф кода для Rust, Python, C и C++**: функции и методы (что принимают, что возвращают, doc-комментарий или docstring), классы, структуры и трейты, наследование (`class B(A)`, `class B : public A`, супертрейты), `impl`, вызовы, импорты и `#include`, использование типов;
- **карта**: `.gitnext/map/**/DIR.md` для каждой директории плюс корневой `AGENTS.md` с инструкцией для агента;
- **дешёвая навигация для агентов**: `outline` (скелет файла без тел), `read` (код одного символа), `impact` (что сломается), MCP-сервер;
- **семантический diff**: изменения на уровне символов; `gitnext commit` дописывает их в сообщение коммита;
- **TUI**: файлы, символы и детали; код с подсветкой, переходы по вызовам, автообновление.

## Установка

```sh
sh scripts/install.sh            # из клона: собирает этот исходник (нужен Rust)
# или, когда репозиторий будет на GitHub и выйдет релиз:
curl -fsSL https://raw.githubusercontent.com/pnnnx/gitnext/main/scripts/install.sh | sh
```

`install.sh` сначала ищет готовый бинарник в GitHub Releases для вашей системы (macOS и Linux, arm64 и x86_64, с проверкой sha256), а если его нет — собирает из исходников через `cargo`. Релизы собирает `.github/workflows/release.yml` при пуше тега `v*`.

Проверка, что всё готово для агента:

```sh
gitnext doctor     # бинарник на PATH и той же версии, индекс, карта, конфиги агентов, сервер модели для loca
```

Каждая проблема выводится с командой, которая её исправляет; код выхода 1, если есть что-то блокирующее. Инструкция, по которой агент может сам всё поставить и подключить, — `docs/AGENT_INSTALL.md`: дайте её агенту и попросите «установи gitnext по этой инструкции».

## Быстрый старт

```sh
cd my-project
gitnext init             # git init (если нужно) + индекс + карта
gitnext setup            # подключить агентов, которые есть в репо (Claude Code, Cursor, loca…)
gitnext                  # TUI
```

В индекс не попадают копии и кэши, даже если нет `.gitignore`: `build/`, `dist/`, `*.egg-info`, `__pycache__`, `.venv`, `target/`, `node_modules/` и т.п. (`build/` и `dist/` остаются, если они закоммичены в git). Настройка в `.gitnext/config`: `index_skip = gen, vendor` — пропускать ещё, `index_keep = build` — не пропускать.

Неизвестную команду gitnext не отдаёт в git вслепую: `gitnext doctr` → «Did you mean `gitnext doctor`?». Привычное `gitnext log -5` тоже работает.

## Git по-человечески

```sh
gitnext status           # что изменилось — словами и по функциям, плюс предложенное сообщение коммита
gitnext add Task::reopen # застейджить одну функцию, а не весь файл (reset — обратно)
gitnext commit           # без -m: предложит сообщение из изменений ([Y]es / [e]dit / [n]o)
gitnext undo             # забрать последний коммит назад, изменения остаются застейдженными
gitnext timeline         # все прошлые точки ветки; --to N — вернуться (файлы не трогаются)
gitnext branches         # насколько каждая ветка впереди/позади и что она меняет
```

Ошибки git переводятся на понятный язык с подсказкой, что делать (нет identity, конфликт, `index.lock`, нечего коммитить). `undo` не даст переписать уже запушенный коммит.

В TUI то же самое: `s` открывает экран изменений (группы «готово к коммиту» / «изменено» / «новые» / «конфликты», под каждым файлом — изменённые функции), `space` стейджит файл или одну функцию, `enter` показывает «было / стало» рядом, `c` открывает коммит с уже написанным сообщением, `U` — отмена коммита, `H` — машина времени, `B` — ветки, `ctrl-p` — список всех действий. При первом запуске показывается короткая памятка.

## Сколько это экономит на самом деле

Замер в двух чатах Claude на одной копии loca (~120k токенов кода) с одинаковыми 6 задачами: архитектура, баг, новая опция с тестом, переименование в 5 файлах, анализ влияния, все тесты.

- Агент без gitnext справился (6/6), прочитав 49 KB вывода (≈12k токенов) — он и так брал куски через `grep`/`sed`, а не файлы целиком. Его же пересчёт «если бы читал через gitnext»: 29 KB, −41%.
- Но чтение кода — лишь ~6% токенов сессии: ~85% уходит на системные инструкции, которые модель перечитывает на каждом шаге. Поэтому главное — меньше шагов, а не короче вывод.
- После этого появился `look`: один вызов отвечает «что это, кто вызывает, что вызывает, какие тесты и как их запустить, что заденет изменение», и целей можно передать несколько. Те же 6 задач через `look` / `edit` / `rename` / `impact`: 6 вызовов инструментов, 22 KB вывода, 6/6 (оговорка: прогон делал я, зная задачи, — свежему агенту понадобится больше шагов).

Найденные в замере ошибки исправлены и закреплены тестами (`crates/gitnext-ops/tests/rename_impact.rs`):
- `rename` теперь меняет и тесты, и импорты внутри функций, и `module.func` (`tt.detect_test_command = …`), и строки в `__all__`, а всё, что ещё пишет старое имя как текст, выводит списком — переименование в loca: 18 мест из 18, все тесты зелёные;
- `impact` больше не идёт по вызовам `x.run()` с неизвестным типом объекта: такие связи показаны отдельно как «maybe» и дальше не разворачиваются;
- `read main` при нескольких `main` просит уточнить, какой.

## Подключить агента

```sh
gitnext setup                    # агенты, найденные в репо (по CLAUDE.md, .cursor, .loca); иначе Claude Code
gitnext setup claude --hooks     # + хуки Claude Code
gitnext setup cursor codex loca  # явно
gitnext brief                    # «на чём остановились»: ветка, незакоммиченные символы, прошлая сессия агента
```

| Агент | Что пишет `setup` |
|---|---|
| Claude Code | `.mcp.json`, блок в `CLAUDE.md`; с `--hooks` — `.claude/settings.json` |
| Cursor | `.cursor/mcp.json`, `.cursor/rules/gitnext.mdc` |
| Codex | печатает блок для `~/.codex/config.toml` (Codex и так читает `AGENTS.md`) |
| loca (llama.cpp / Ollama) | компактный блок в `AGENTS.md` (loca кладёт его в промпт); с `--tools` ещё `.loca/config.json` (MCP, профиль `lite`) и `LOCA.md` |

Блоки ограничены маркерами `gitnext:agent`, остальной текст файлов не трогается, повторный запуск ничего не дублирует.

Хуки Claude Code (`--hooks`):
- `gitnext hook read` — когда агент читает большой файл кода целиком, первый раз ему возвращается outline с номерами строк, чтобы он прочитал только нужное. Повторный такой же `Read` проходит. Порог — `GITNEXT_HOOK_MIN_TOKENS` (2000).
- `gitnext hook session-start` — в начале сессии в контекст попадает `brief`.

Экономия каждого вызова MCP передаётся в `_meta` ответа (`gitnext/tokens`, `gitnext/naive_tokens`): её видят клиент и журнал, а модель за неё не платит.

## Локальные модели (llama.cpp, Ollama)

Для моделей на 3–14B с контекстом 8–32k:

- `gitnext mcp --profile lite` — три инструмента, у каждого только строковые параметры (весь список ~1.2 KB):
  - `look(what)` — один вход для всего чтения: файл или папка → функции и классы с номерами строк; имя функции или класса (`parse_date`, `Task.reopen`, даже `class Store`) → её код и кто её вызывает; текст ошибки или traceback → место, где она случилась; любые слова → где они встречаются;
  - `replace(symbol, code)` — заменить функцию целиком;
  - `add_after(symbol, code)` — добавить код после функции.
  Ответ ограничен 1500 токенами (`GITNEXT_MCP_MAX_TOKENS`), в конце каждого ответа — подсказка, что вызвать дальше.
- `gitnext setup loca` переводит блок gitnext в `AGENTS.md` в компактный вид (~0.9 KB вместо ~3.5 KB: области в порядке зависимостей и главные символы) — loca кладёт этот файл в системный промпт, а у неё лимит 6000 символов. MCP-инструменты по умолчанию не подключаются (см. замеры ниже); `gitnext setup loca --tools` добавит их в `.loca/config.json` и примеры вызовов в `LOCA.md`.
- `explain` умеет работать с любым OpenAI-совместимым сервером: `GITNEXT_OPENAI_BASE=http://127.0.0.1:8080/v1 gitnext explain` (llama-server, LM Studio, vLLM). Блоки `<think>` из ответа вырезаются.
- Память: сам gitnext занимает около 20 MB (индекс в SQLite, граф в памяти) — на фоне 5 GB модели это незаметно. Десктоп-версия отложена по той же причине: память нужна модели.

Проверка на настоящем агенте — `integrations/loca/bench_gitnext.py`: гоняет бенчмарк loca в режимах `off` (как есть), `map` (только карта) и `mcp` (карта + инструменты), в том числе на задачах внутри копии самого loca (~120k токенов кода, в 16k контекст не помещается).

```sh
python3 integrations/loca/bench_gitnext.py --loca ~/Developer/loca \
    --backend llamacpp --host http://127.0.0.1:8080 --ctx 16384 --time-scale 3 \
    --tasks big,failing_test,find_definition --modes off,mcp --out runs/gitnext.json
```

Замеры на стоковой Qwen3.5-4B (Q4_K_M, llama.cpp, контекст 16k, 2 ядра CPU), по одному прогону на вариант:

| Задача | Без gitnext | Карта (+ инструменты gitnext) |
|---|---|---|
| найти класс в копии loca (~120k токенов кода) | ✓ 3 шага · 12.5k токенов · 273 с | ✓ 2 шага · 4.4–4.9k токенов · 55–97 с (3 прогона) |
| исправить падающий тест там же | ✓ 12 шагов · 36k · 830 с | ✓ 8–12 шагов · 23–43k · 724–922 с (3 прогона) |
| исправить тест в маленьком проекте | ✓ 7 шагов · 17k | ✓/✗ 6–18 шагов · 17–68k (3 прогона) |
| найти определение в маленьком проекте | ✓ 3.9k | ✓ 4.6k |

Что из этого следует:
- устойчивый выигрыш даёт только карта в промпте и только там, где модель иначе начинает с обзора всего репозитория: в 3 раза меньше токенов и быстрее;
- в остальных задачах разница меньше разброса между одинаковыми прогонами (до 2×); нужны повторы (`--repeat 3`);
- за 14 прогонов модель ни разу не вызвала инструменты gitnext — ни когда они были за `load_tools`, ни когда стояли прямо в её списке (`mcp-core`, патч `integrations/loca/core_tools.patch` для loca). У loca есть свои `repo_map` и `read_symbol`, и 4B держится за них. Поэтому `setup loca` по умолчанию подключает только карту, а инструменты gitnext нужнее агентам без своей навигации по коду: Claude Code, Cursor, Codex.

## Агенту: найти → понять → поправить

```sh
gitnext look Agent.execute brief loca/config.py   # одним вызовом: код, кто вызывает, что вызывает, тесты и команда для них, влияние
gitnext overview                         # первый вызов в незнакомом репо
gitnext map src/net && gitnext outline src/net/http.rs
gitnext read Client::send                # только код символа (Name@LINE для перегрузок)
echo "$NEW_CODE" | gitnext edit replace Client::send     # без чтения файла; ломающая правка отклоняется
gitnext rename Client::send send_request # определение и все однозначные ссылки
gitnext impact Client::send && gitnext tests-for Client::send   # кого задело, какие тесты гонять
cargo test 2>&1 | gitnext locate         # ошибка → функции и код
```

В MCP то же самое доступно как инструменты. Сервер помнит, что уже отдал: повторный `read` неизменённого кода возвращает одну строку, а `changes` показывает только то, что поменялось с прошлого вызова.

## Человеку: понять проект за минуту

```sh
gitnext overview      # языки, области, точки входа, зависимости, активность, здоровье
gitnext activity      # кто и что менял;    gitnext hotspots  — рискованные файлы
gitnext history Sym   # когда символ появился и как менялся (с переименованиями)
gitnext changelog main..feature          # что добавлено и что сломает внешние вызовы
gitnext dead · gitnext cycles · gitnext entrypoints
gitnext journal       # что делал агент: прочитал, поправил, сколько токенов сэкономил
```

TUI открывается с обзора, показывает код с подсветкой и позволяет ходить по вызовам. Символы, которые агент читал или правил, подписаны словами.

Всё написано словами и стрелками, без таблиц и значков:
- папка: что она использует (`→`) и кто использует её (`←`), файлы ровными колонками, функции в виде `run(args: &[String]) → Result<()>` — входы жёлтым, выход зелёным;
- функция: `takes` — каждый параметр отдельной строкой, `returns →` — что возвращает, `← called by` и `→ calls` — по кому можно перейти;
- класс или тип: что в нём лежит, `is a → Animal`, `implements → Shape, Display`, `← implemented by …`, методы по интерфейсам;
- весь проект (`o`): слои зависимостей — снизу фундамент, который ни от кого не зависит, сверху то, что использует остальное; циклы показываются отдельно.

## Экономия токенов

Агент сначала ориентируется по карте, потом смотрит скелет файла и только после этого читает нужный символ:

```sh
gitnext map crates/core          # назначение, файлы, API директории
gitnext outline src/storage.rs   # сигнатуры с номерами строк, без тел
gitnext read Storage::save FileStore::open   # только код этих символов
gitnext impact Task::complete    # кого затронет изменение
```

Замеры на настоящих проектах (≈ токены):

| Проект | Весь исходник → вся карта | Большой файл → `outline` | `read` одной функции |
|---|---|---|---|
| ripgrep (Rust) | 470k → 64k | 10.3k → 2.1k | 229 |
| requests (Python) | 102k → 11k | 8.5k → 1.3k | ~1k |
| cJSON (C) | 134k → 8.7k | 20.2k → 3.2k | 35 |
| tinyxml2 (C++) | 66k → 14k | 19.8k → 3.5k | 87 |

Ещё несколько приёмов экономии:
- когда вывод идёт не в терминал (агент вызывает gitnext через shell), печатается компактный текст без цвета и без повторов;
- тестовый код схлопывается в счётчик (`+5 tests`), а флаг `--tests` раскрывает его;
- `--json` выдаёт компактный JSON, `--pretty` добавляет отступы.

## MCP

```sh
gitnext setup            # или только .mcp.json: gitnext mcp --install
gitnext mcp --profile lite   # для маленьких локальных моделей
```

Claude Code подхватит сервер при запуске в этой папке (один раз нужно подтвердить). Для Cursor тот же блок кладётся в `.cursor/mcp.json`:

```json
{ "mcpServers": { "gitnext": { "command": "gitnext", "args": ["mcp"] } } }
```

Инструменты:
- **один вызов вместо нескольких:** `look` — для функции или класса сразу код, вызывающие, вызываемые, тесты с командой запуска и влияние; для файла или папки — скелет; для ошибки — место; можно несколько целей за раз;
- **понять проект:** `overview`, `entrypoints`, `map`, `outline`;
- **найти и прочитать:** `read`, `show`, `search`, `callers`, `callees`, `impact`, `hierarchy`, `deps`, `tests_for`, `locate`, `context`;
- **править:** `replace_symbol`, `insert_after`, `delete_symbol`, `rename_symbol`;
- **описать код:** `annotate`;
- **изменения и история:** `brief`, `changes`, `since`, `diff`, `history`, `changelog`.

Сервер держит индекс открытым, подхватывает изменённые файлы и пишет журнал в `.gitnext/journal.jsonl`.

### explain: смысл кода без документации

Описания хранятся в `.gitnext/notes.tsv` (файл коммитится) и привязаны к хешу кода, поэтому устаревают, когда код меняется. В выводе они помечены `≈`. Источники:
- агент через MCP-инструмент `annotate` (бесплатно: код он уже прочитал);
- `GITNEXT_LLM_CMD='claude -p'` (любая команда: промпт на stdin, ответ в stdout);
- `ANTHROPIC_API_KEY` (модель задаётся `GITNEXT_MODEL`);
- `GITNEXT_OLLAMA_MODEL` (локальный Ollama);
- `GITNEXT_OPENAI_BASE` (любой OpenAI-совместимый сервер: llama.cpp `llama-server`, LM Studio, vLLM; модель — `GITNEXT_OPENAI_MODEL`).

### Точный граф (LSP)

По умолчанию ссылки разрешаются по именам за миллисекунды. `gitnext lsp` отправляет языковому серверу только неоднозначные места и кэширует ответы, пока файл не изменится. На ripgrep это 3000 вызовов за 28 секунд. Команды серверов настраиваются через `GITNEXT_LSP_RUST`, `GITNEXT_LSP_PYTHON` и `GITNEXT_LSP_C`.

## Команды

| Команда | Что делает |
|---|---|
| `gitnext` / `gitnext tui` | интерактивный интерфейс |
| `gitnext init [path]` | создать репозиторий, проиндексировать, написать карту |
| `gitnext status [-s]` | изменения словами и по функциям, предложенное сообщение (`-s` — коротко, как git) |
| `gitnext add [paths\|Sym]` · `reset <paths\|Sym>` · `log [-n N]` | stage / unstage файла или одной функции |
| `gitnext commit [-m MSG] [-a] [--no-map] [--no-semantic]` | коммит; без `-m` предлагает сообщение; карта обновляется и стейджится сама |
| `gitnext msg` | только предложенное сообщение коммита |
| `gitnext undo` · `timeline [--to N]` · `branches` | отменить коммит, вернуться к прошлой точке, карточки веток |
| `gitnext diff [--staged] [--full]` | семантический diff: `+` добавлено, `-` удалено, `~` сигнатура, `*` тело или доки |
| `gitnext index` | инкрементальная индексация |
| `gitnext map [dir]` | перегенерировать карту или вывести карту директории |
| `gitnext outline <file\|dir> [-a]` | скелет: сигнатуры и однострочные описания без тел |
| `gitnext read <Sym>…` | исходник символов (с doc-комментариями и диапазоном строк) |
| `gitnext show <Sym> [--full]` | сигнатура, доки, callers, callees, типы, иерархия |
| `gitnext search <text>` | поиск символов по имени и документации |
| `gitnext symbols [path] [-k kind] [--pub]` | список символов |
| `gitnext callers <Sym>` · `callees <Sym>` | кто вызывает и что вызывает |
| `gitnext impact <Sym> [-d 3]` | обратные зависимости, затронутые файлы и тесты |
| `gitnext hierarchy <Type>` | базовые классы, интерфейсы, реализации, наследники, методы |
| `gitnext deps [dir]` | зависимости директории |
| `gitnext context "<задача>" [-t 6000]` | релевантный код под бюджет токенов |
| `gitnext edit replace\|insert-after\|delete <Sym>` | правка одного символа (код из stdin), с проверкой синтаксиса |
| `gitnext rename <Sym> <new> [--dry-run]` | переименовать во всех однозначных местах, предупредить о переопределениях |
| `gitnext overview` · `activity` · `hotspots` · `dead` · `cycles` · `entrypoints` | понимание проекта |
| `gitnext history <Sym>` · `changelog a..b` · `since <rev>` | семантическая история |
| `gitnext locate` (stdin) · `tests-for <Sym>` | ошибка → код; тесты и команда запуска |
| `gitnext explain [path] [--dry-run]` · `annotate <Sym\|dir:path> "текст"` | описания для кода без документации (`.gitnext/notes.tsv`) |
| `gitnext lsp [--lang rust\|python\|c]` | точный граф: неоднозначные вызовы через rust-analyzer / pyright / clangd |
| `gitnext journal [-n 3]` | журнал агента |
| `gitnext bench` | замер экономии токенов на этом репозитории |
| `gitnext mcp [--install] [--profile lite]` | MCP-сервер на stdio |
| `gitnext setup [agents…] [--all] [--hooks]` · `doctor` · `brief` · `hook read\|session-start` | подключение агентов, проверка готовности, сводка для начала сессии, хуки |
| `gitnext <любая другая>` | передаётся в системный `git` |

Символ можно указать как `Name`, `Type::method`, `Type.method` (в стиле Python) или полным именем. Глобальные флаги: `--json`, `--pretty`, `--tests`, `--full`, `-C <dir>`.

## Клавиши TUI

- **Навигация:** `tab` переключает панели, `j k` двигают курсор, `l →` и `h ←` входят и выходят, `/` ищет.
- **Панель деталей:** `j k` ходят по ссылкам (callers, callees, наследники, методы), `enter` переходит, `b` возвращает назад, `pgup/pgdn` прокручивают.
- **Git:** `s` — изменения (`space` stage/unstage файла или функции, `enter` — было/стало), `c` — коммит с предложенным сообщением (`ctrl-u` очищает), `U` — отменить коммит, `H` — машина времени, `B` — ветки, `d` — семантический diff.
- **Остальное:** `ctrl-p` или `:` — все действия списком, `o` — обзор, `a` — журнал агента, `m` пишет карту, `r` переиндексирует, `?` — клавиши, `q` выходит.

Индекс обновляется сам, когда вы правите файлы в редакторе.

## Проверка качества

- `crates/gitnext-parse/tests/fixtures/` — эталоны парсинга для Rust, Python, C и C++: исходник и рядом `*.expected` со всеми символами (вид, строки, сигнатура, входы, выход, родитель, интерфейс) и связями. После намеренного изменения парсера: `GITNEXT_BLESS=1 cargo test -p gitnext-parse --test fixtures` и просмотр diff.
- `.github/workflows/ci.yml` — clippy с `-D warnings`, все тесты и запуск бинарника на Ubuntu и macOS.

## Языки

| Язык | Файлы | Что извлекается |
|---|---|---|
| Rust | `.rs` | fn, методы, struct/enum/union (поля, варианты), trait и супертрейты, `impl Trait for`, mod, type, const, macro, `use`, вызовы (в том числе внутри макросов) |
| Python | `.py` `.pyi` | функции и методы с аннотациями и значениями по умолчанию, декораторы, классы и базовые классы, поля (аннотации, `self.x` в `__init__`), docstring, константы `UPPER_CASE`, импорты (в том числе относительные), вызовы, создание экземпляров |
| C | `.c` `.h` | функции и прототипы, `static`, struct/union/enum, typedef, `#define`, `#include`, вызовы |
| C++ | `.cpp` `.cc` `.hpp` `.hh` … | namespace, class/struct с доступом и полями, базовые классы, методы (в классе и `Foo::bar` вне его), конструкторы и деструкторы, шаблоны, `using`, `new T(...)` |

Экспортные макросы (`FOO_API`, `FOO_PUBLIC(T)`, `__declspec`, `__attribute__`) вычищаются перед разбором, номера строк при этом сохраняются. Тестовый код (`#[test]`, `mod tests`, `test_*.py`, `tests/`, `TEST(...)`) помечается и не попадает в карту.

## Устройство

```
crates/
  gitnext-parse   tree-sitter → символы и рёбра (rust.rs, python.rs, cfamily.rs)
  gitnext-index   SQLite-индекс .gitnext/index.db, граф, разрешение ссылок, impact, семантический diff
  gitnext-core    git через libgit2 (git2)
  gitnext-docs    генерация DIR.md / AGENTS.md
  gitnext-ops     сценарии (commit с картой, diff, context) и компактный вывод (render.rs)
  gitnext-tui     ratatui-интерфейс
  gitnext-cli     бинарник `gitnext` (clap) и MCP-сервер (mcp.rs)
```

- `.gitnext/index.db` это локальный кэш, он в `.gitignore`. Карта `.gitnext/map/` и `AGENTS.md` коммитятся.
- Ссылки разрешаются по именам с учётом области видимости: свой крейт или импортированный пакет, глобальное пространство C и C++, `self.` и `this->`. Вызов метода на неизвестном объекте помечается как неоднозначный, а не угадывается.
